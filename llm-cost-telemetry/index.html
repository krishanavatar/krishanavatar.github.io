Cost Telemetry First: Tracking Per-Model LLM Spend Before You Optimize It

Caching, routing, and prompt compression only work once you know which model, which document type, and which cache state is generating your bill. This is the tracking layer I built before touching any of those levers, and what it found before it found the fix.

krishanavatar.github.io / July 2026 / 13 min read
CONTEXT

This is drawn from building cost telemetry for a multi-provider document intelligence pipeline — the same platform I wrote about in LLM Cost Optimization in Production. That post covered the three levers that cut spend by 64%. This one covers the instrumentation that made pulling any of those levers a decision instead of a guess.

What Cost Telemetry Has to Answer
  • 1
    Which model, exactly — not "OpenAI" or "the LLM," but the specific model ID that served the request, since a mini and a frontier model on the same provider can differ in price by 15x.
  • 2
    Which document type and pipeline stage — extraction, classification, and validation calls have different cost profiles, and a blended number hides which one is actually expensive.
  • 3
    Cache hit or miss — the same token count is a different dollar amount depending on whether it landed in cache, and a system that can't distinguish the two is measuring the wrong thing.
01 — The Problem

The Bill Doesn't Tell You Where the Money Went

The first version of cost visibility on our document pipeline was a single number: total LLM spend for the month, pulled from the provider billing dashboards and added together across three vendors. It told us the number was too high. It told us nothing about why.

That's the trap with aggregate billing. A provider invoice bills by API key or by project, not by document type, not by pipeline stage, not by which of your six configured models actually served each request. When finance asks why the number went up 20% month over month, "the LLM calls got more expensive" is not an answer anyone can act on. Somebody has to go find the actual cause, and without instrumentation, that search is manual: pull sample logs, guess at patterns, re-run a few requests by hand and hope the sample generalizes.

We did that manual search twice before deciding it wasn't sustainable. The second time, a spend spike traced back to a single document type that had quietly started routing to a frontier model after a schema change, and it took four days to find. That's the point at which telemetry stopped being a nice-to-have and became a prerequisite for touching the cost problem at all.

02 — Diagnosis

Why the Blended Average Lies

Our blended cost was roughly $0.018 per document before any optimization work started. That number is useless on its own, because it assumes every document costs about the same to process, and they don't. A clean, single-page form and a ten-page multi-column statement do not touch the same number of tokens, the same model tier, or the same retry rate.

Once we broke the blended figure down by document type and model, the picture looked nothing like the average suggested. A minority of document types were responsible for a majority of spend, and the reason wasn't document complexity, it was routing: certain types were pinned to a frontier model for historical reasons nobody had revisited.

Document type % of volume % of spend Model tier used Cost / doc
Standard single-page form 54% 21% Cheap tier $0.007
Multi-page statement 28% 33% Mixed $0.021
Legacy claim format 11% 37% Frontier (pinned) $0.063
Everything else 7% 9% Mixed $0.024

The legacy claim format was 11% of volume and 37% of spend, pinned to a frontier model since a reliability incident more than a year earlier that nobody had re-tested since. Nothing about this was visible in the blended average. It only showed up once cost was attributed per document type and per model, which meant the attribution layer had to exist before the optimization work could be scoped, let alone prioritized.

03 — Instrumentation

Instrumenting the Call, Not the Invoice

The fix starts at the point where the request actually happens, not at the point where the bill arrives. Every call into a provider SDK already returns a usage object: input tokens, output tokens, and for providers that support it, cache read and cache write tokens. That object is thrown away by default the moment the response is parsed for its content. The instrumentation is simply refusing to throw it away.

I wrapped every provider call in a single decorator that captures the usage object alongside the context that the usage object itself doesn't know: which document type triggered the call, which pipeline stage it came from, and which tenant it belongs to. None of that context lives on the response. It has to be attached at the call site.

Python — usage capture decorator
import functools
import time
from dataclasses import dataclass, asdict

@dataclass
class UsageEvent:
    model:              str
    provider:           str
    doc_type:           str
    pipeline_stage:     str
    tenant_id:          str
    input_tokens:       int
    output_tokens:      int
    cache_read_tokens:  int
    cache_write_tokens: int
    latency_ms:         float
    estimated_cost:     float

def track_usage(doc_type: str, pipeline_stage: str, tenant_id: str):
    def decorator(call_fn):
        @functools.wraps(call_fn)
        def wrapper(model: str, provider: str, *args, **kwargs):
            t0 = time.time()
            response = call_fn(model, provider, *args, **kwargs)
            latency = (time.time() - t0) * 1000

            usage = response.usage
            event = UsageEvent(
                model=model,
                provider=provider,
                doc_type=doc_type,
                pipeline_stage=pipeline_stage,
                tenant_id=tenant_id,
                input_tokens=usage.input_tokens,
                output_tokens=usage.output_tokens,
                cache_read_tokens=getattr(usage, "cache_read_input_tokens", 0),
                cache_write_tokens=getattr(usage, "cache_creation_input_tokens", 0),
                latency_ms=latency,
                estimated_cost=estimate_cost(model, usage),
            )
            emit(event)  # → metrics pipeline, see below
            return response
        return wrapper
    return decorator

The important design choice is that doc_type, pipeline_stage, and tenant_id are passed in at the decoration point, where the calling code already knows them, rather than inferred later from logs. Inference after the fact is where attribution efforts usually stall, because reconstructing context from a raw request log is unreliable and slow. Capture it while it's still in scope.

04 — Attribution Model

Choosing the Attribution Dimensions

Every usage event carries six dimensions: model, document type, pipeline stage, tenant, prompt template version, and cache state. That's a deliberate, small set. It's tempting to tag events with everything available — request ID, user ID, feature flag state, arbitrary deployment metadata — but every additional dimension multiplies the number of distinct time series a metrics backend has to store, and most of that cardinality never gets queried.

The six we kept map directly to decisions someone would actually make: model tells you what to route, document type tells you what to route it based on, pipeline stage tells you where in the flow the cost concentrates, tenant tells you who to bill or throttle, prompt template version tells you whether a cost step-change traces back to a specific prompt edit rather than a shift in traffic mix, and cache state tells you whether caching is behaving as designed. Anything that doesn't map to a decision is a dimension not worth the cardinality cost.

Cache state deserves its own callout because it's the dimension most likely to be modeled wrong. A request isn't simply "cached" or "not cached" — it can have a mix of cache-read tokens and normal-priced tokens in the same call, and the cache write itself carries a cost premium on some providers. Treating cache state as a spectrum rather than a boolean is what let us later notice that one model's effective cache hit rate was far below the other two, well before that gap showed up as a cost anomaly.

On tenant-level attribution

If your platform is multi-tenant, tag by tenant from day one even if nobody's asking for per-tenant billing yet. Retrofitting tenant attribution onto historical usage data is close to impossible, because the context that would let you reconstruct it is usually gone by the time someone asks for it.

05 — The Telemetry Pipeline

Building the Telemetry Pipeline

Capturing the usage event is half the problem. The other half is getting it into something queryable without adding latency to the request path the event came from. We emit each event asynchronously to a Prometheus pushgateway, tagged by the low-cardinality subset of those dimensions — model, provider, document type, pipeline stage, and cache state — and let Grafana do the aggregation.

Python — async metric emission
from prometheus_client import Counter, Histogram
import asyncio

LLM_COST_TOTAL = Counter(
    "llm_cost_usd_total",
    "Estimated LLM spend in USD",
    ["model", "provider", "doc_type", "pipeline_stage", "cache_state"]
)
LLM_TOKENS_TOTAL = Counter(
    "llm_tokens_total",
    "Tokens processed",
    ["model", "direction", "cache_state"]
)
LLM_LATENCY = Histogram(
    "llm_call_latency_ms",
    "Per-call latency",
    ["model", "pipeline_stage"]
)

async def emit(event: UsageEvent):
    cache_state = "hit" if event.cache_read_tokens > 0 else "miss"

    LLM_COST_TOTAL.labels(
        model=event.model, provider=event.provider,
        doc_type=event.doc_type, pipeline_stage=event.pipeline_stage,
        cache_state=cache_state,
    ).inc(event.estimated_cost)

    LLM_TOKENS_TOTAL.labels(model=event.model, direction="input", cache_state=cache_state).inc(event.input_tokens)
    LLM_TOKENS_TOTAL.labels(model=event.model, direction="output", cache_state="n/a").inc(event.output_tokens)
    LLM_LATENCY.labels(model=event.model, pipeline_stage=event.pipeline_stage).observe(event.latency_ms)

Notice that tenant ID and prompt template version aren't Prometheus labels. They're high-cardinality relative to model and document type, and pushing them into the same time series would blow up storage on the metrics backend. Instead, every usage event is also published as a JSON message to a Kafka topic, consumed by a small worker that writes it as a row into ClickHouse. ClickHouse is built for exactly the cardinality Prometheus isn't: one row per LLM call, tenant and prompt version included, queried with plain SQL for anything ad hoc rather than pre-aggregated into a fixed set of dashboard panels.

SQL — ClickHouse event table
CREATE TABLE llm_usage_events (
    ts                  DateTime,
    model               LowCardinality(String),
    provider            LowCardinality(String),
    doc_type            LowCardinality(String),
    pipeline_stage      LowCardinality(String),
    tenant_id           String,
    prompt_version      String,
    cache_state         LowCardinality(String),
    input_tokens        UInt32,
    output_tokens       UInt32,
    cache_read_tokens   UInt32,
    cache_write_tokens  UInt32,
    latency_ms          Float32,
    estimated_cost      Float64
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(ts)
ORDER BY (tenant_id, model, ts);

-- cost per tenant per day, last 30 days -- the chargeback query
SELECT
    toDate(ts)              AS day,
    tenant_id,
    round(sum(estimated_cost), 2) AS cost_usd
FROM llm_usage_events
WHERE ts >= now() - INTERVAL 30 DAY
GROUP BY day, tenant_id
ORDER BY day DESC, cost_usd DESC;

The rule of thumb: dimensions you want a real-time alert on go in the metrics labels; dimensions you want for ad hoc billing, chargeback, or audit queries go in ClickHouse, where cardinality is cheap and SQL replaces a fixed panel set.

Or Don't Build the Pipeline Yourself

Everything above is a from-scratch build, and from-scratch is the right call when your attribution dimensions are specific to your own pipeline — document type and pipeline stage aren't concepts any off-the-shelf tool knows about. It is not the only option, and it's worth knowing what the alternatives actually give you before deciding to write a decorator and stand up a Kafka topic.

Approach Gives you out of the box You still build Best fit
Custom (this post) Full control over attribution dimensions; no new dependency in the request path Capture, transport, storage, dashboards — all of it Pipeline-specific dimensions like document type or tenant
LiteLLM One SDK across 100+ providers, per-call cost calculated for you, proxy mode with per-key budgets and rate limits Long-term storage and dashboards beyond its built-in views; custom business dimensions Multi-provider routing where per-model cost math is the main pain point
Langfuse Hosted traces, cost, prompt versioning, and eval scores in one dashboard Deep pipeline-specific dimensions unless modeled as trace metadata Teams that want tracing, cost, and prompt eval without assembling three tools
OpenTelemetry (GenAI conventions) Vendor-neutral span attributes (gen_ai.usage.input_tokens, etc.) that plug into an existing OTel backend The GenAI semantic conventions are still stabilizing; per-provider instrumentation coverage varies Orgs already standardized on OTel who want LLM calls in the same backend as every other service

We built custom because the dimensions that mattered most — document type, pipeline stage, tenant — aren't things a general-purpose LLM observability tool models natively, and Prometheus and ClickHouse were already load-bearing pieces of our stack. If I were starting today with a simpler pipeline and no existing metrics infrastructure, I'd reach for LiteLLM's proxy plus Langfuse before writing a single decorator. The build-versus-buy line isn't about maturity, it's about how much of your cost structure is generic provider math versus specific to your own pipeline.

06 — What It Found

What the Dashboards Surfaced

Within the first two weeks of live telemetry, three things showed up that four days of manual log-digging had missed entirely.

Finding 1

A pinned frontier route nobody revisited

The legacy claim format from the earlier table, still routed to a frontier model over a year after the reliability issue that justified it had been fixed elsewhere in the pipeline.

Finding 2

A cache hit rate 40 points below its peers

One provider's cache hit rate sat at 52% against 90%+ for the others, traced to a system prompt that included a per-request timestamp in the cacheable prefix.

Finding 3

One tenant driving disproportionate spend

A single tenant generating 6% of document volume but 19% of spend, because their document mix skewed heavily toward the expensive multi-page statement type.

None of these three are exotic bugs. They're the ordinary way cost drifts in a system nobody is watching closely: a decision made under one set of conditions outlives the conditions that justified it. What telemetry changes isn't the existence of that drift, it's the time between the drift happening and someone noticing. Four days of manual digging became something visible on a dashboard in the first sprint after the metrics went live.

07 — Guardrails

Turning Dashboards Into Alerts

A dashboard someone has to remember to check is a dashboard that gets checked at month-end, which is exactly the cadence we were trying to escape. The metrics only became useful operationally once we set alerting thresholds on top of them: per-model daily spend, per-tenant spend velocity, and cache hit rate floor per model.

PromQL — alert rules
# Per-model daily spend exceeds 150% of its 7-day rolling average
- alert: LLMModelCostSpike
  expr: |
    increase(llm_cost_usd_total[1d])
      > 1.5 * avg_over_time(increase(llm_cost_usd_total[1d])[7d:1d])
  labels:
    severity: warning

# Cache hit rate for a model drops below 70%
- alert: LLMCacheHitRateLow
  expr: |
    sum(rate(llm_tokens_total{cache_state="hit"}[1h])) by (model)
      / sum(rate(llm_tokens_total{direction="input"}[1h])) by (model)
      < 0.70
  labels:
    severity: warning
What this caught in practice

A retry loop on a malformed document was silently re-sending the same request to a frontier model six times before failing validation and giving up. The daily cost-spike alert fired within an hour of that document type entering the queue; without it, the same failure mode would have shown up as an unexplained bump on the following month's invoice.

08 — Beyond the Invoice

What This Unlocks Beyond the Line Item

Cost was the reason this got built. It wasn't the only thing it turned out to answer. Once the same event stream exists, four questions that had nothing to do with the original mandate get answered for free.

  • Quota and rate-limit avoidance. Per-model, per-provider call volume in real time means you can see a provider approaching its rate limit before requests start failing, and shift new traffic to a provider with headroom. Without it, you find out about the limit from a wave of 429s in production, which is the worst possible time to learn it.
  • Regression detection. A prompt template edit that silently doubles output tokens, or a schema change that pushes more documents onto a frontier-tier model, shows up as a step change on a per-model panel within the hour it ships. Tagging events with prompt template version means the step change points at the deploy that caused it instead of triggering a vague investigation days later.
  • Chargeback and showback. With tenant-level cost already captured, "we spent $40k on LLM calls this month" becomes "team X's feature spent $6k of it" — a rollup query against the ClickHouse table, not a project. Whether that number goes into an internal chargeback or a lighter-weight showback report, the attribution work is already done before anyone asks for it.
  • Model routing with a number behind it. Telemetry pairs cost against accuracy or error rate captured from the same events, so "route this document type to a cheaper model" stops being a hunch and becomes "the cost delta is 8x and the accuracy delta on our benchmark is within noise." That's the reasoning that justified the routing decisions in the companion post — it existed because the attribution layer existed first.
09 — Failure Modes

Where This Breaks

Cost telemetry is not free to run, and it has its own ways of going wrong.

  • Cardinality explosion. Every attribution dimension you add multiplies the number of time series the metrics backend has to store and query. Model × document type × pipeline stage × cache state is already a meaningful number of series; adding request-level or user-level tags to the same metrics store, rather than to a separate log, is the most common way teams make their observability stack more expensive than the thing it's observing.
  • Retry and fallback double-counting. A request that fails on one model and retries on another produces two usage events for what the business considers a single logical operation. If your cost dashboard isn't explicit about this, "cost per document" quietly becomes "cost per attempt," and the two diverge exactly when retries spike, which is precisely when you need the number to be trustworthy.
  • Emission overhead on the request path. Synchronous metric emission adds latency to every call, however small. Fire the emission asynchronously, and make sure a metrics-pipeline outage degrades to "we lose some visibility" rather than "we lose some requests."
10 — Takeaway

The Frame to Leave On

Cost optimization is a decision problem, and decisions need attribution before they need levers. A blended average per document tells you the size of the problem without telling you its shape, and every optimization built on top of a shapeless problem is a guess dressed up as a plan.

The instrumentation itself is not complicated: capture the usage object the provider already gives you, attach the context that only the call site knows, and keep the attribution dimensions to the ones that map to an actual decision. The discipline is in doing it before the optimization work starts, not after someone asks why the bill went up.

Everything downstream — caching, routing, compression — is easier to justify and easier to calibrate once the telemetry exists. Build the meter before you build the fix.
